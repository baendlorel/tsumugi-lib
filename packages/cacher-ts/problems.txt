==================

[严重-1] 装饰器依赖 context.metadata，仍有三种情况直接抛 TypeError
  位置：src/decorator.ts:55-63（Cache）、src/decorator.ts:100（SubCache）
  a)【新】用 tsc 编译时，所有带 @Cache 的类在【定义时】就抛错（运行时验证）：
       Node 24 没有 Symbol.metadata。tsc 的降级输出是
       `_metadata = Symbol.metadata ? Object.create(null) : void 0`，于是 ctx.metadata 为 undefined，
       60 行 `(ctx.metadata as Metadata)[sym] = …` → "Cannot set properties of undefined (setting 'Symbol()')"。
       esbuild/tsdown 能用只是因为它们自带 `Symbol.for('Symbol.metadata')` 兜底。
       README 写的是“标准 TC39 装饰器、关掉 experimentalDecorators 即可”，并没有说只支持 esbuild 系。
       （这就是上一轮“附：没有 Symbol.metadata 的环境”那一条，实测确认会出现。）
  b) 100 行 `?.[sym].instanceToCacheMap` 仍然少了第二个 `?.`（上一轮的 c 没改）：
       类里没有任何 @Cache 时，抛 "Cannot read properties of undefined (reading 'instanceToCacheMap')"，
       到不了下一行本该给出的 `'cacheMap' for "a" not found.`。
  c)【新】父类写 @SubCache、子类写 @Cache（抽象基类声明派生视图、子类提供数据源）同样抛 b 的 TypeError：
       父类装饰器拿到的是父类的 metadata 对象，子类的 [sym] 写在子类 metadata 上，父类看不到。
  修复建议：map 本来就以实例为键，根本不需要 metadata。
        改成模块级的 `const instanceToCacheMap = new WeakMap<object, Map<string | symbol, Cacher>>()`，
        @Cache/@SubCache 都直接查它：a/b/c 一起消失，SubCache 初始化器里缓存 cacheMap 的逻辑也可以删掉。
        只有想在“类定义时”就检测重复 id 时才需要 metadata，那时也要处理 metadata 为 undefined 的情况。

二、高

[高-1] @SubCache / getSub 仍不会触发父缓存的 TTL 刷新
  位置：src/cacher.ts:175-179
  现象（运行时验证）：@Cache({ttl:50}) + @SubCache，读过一次派生值后等待 80ms 再读：
        派生值不变、getter 调用次数不变（仍为 1）；直接用 Cacher.getSub 结果相同。
  原因：getSub 先走 `Object.is(sub.parent, this.cache)` 快速返回，只有 parent 变化时才 `await this.get()`；
        “父值没变”是常态，所以永远不检查 ttl，只读派生视图的用法等于永不过期。
  修复：把 `const parent = await this.get()` 放到判等之前（过期时 get 内部 reload 并等待新值），
        再用 `Object.is(sub.parent, parent)` 判断（这样 175 行的 `this.cache !== empty` 也可以去掉，get 会先抛未初始化）。
  如果就是想“派生视图不续期”，请在 README 里明确写出来。

[高-2]【新】装饰器的类型签名太宽：@Cache 接受同步方法而类型说谎；README 的 @SubCache 写法编译不过
  位置：src/decorator.ts:10-13（MethodCacheDecorator）、src/decorator.ts:87-88（SubCache）
  类型验证：
    - `@Cache({id:'x'}) m(): number { return 1 }` 编译通过，`const n: number = obj.m()` 也通过，
      运行时却是 Promise<number>。提交 8974f50 说“锁定返回值为 Promise”，但只锁在了 50 行内部函数的参数上，
      对外的 MethodCacheDecorator 是 `(target: (...args: any[]) => any, …)`，限制被抹掉了。
      （同步方法还会触发中-1：同步抛一次错，缓存就永久卡死。）
    - README 的写法 `@SubCache('cfg') adminNames(cfg: ConfigShape) { return …string[] }` 报 TS1270
      （装饰器返回 Promise，无法赋给 `(cfg) => string[]`）；`config.adminNames()` 不传参报 TS2554。
      `async v(cfg: Cfg)` 能声明，但调用 `obj.v()` 仍报 TS2554。
      实测能编译通过的只有 `async view(cfg?: Cfg): Promise<R>` 这一种，而它正好违反 JSDoc 的
      “Decorated method must be SYNC”，README 也没写。
  修复建议（已用 tsc 验证：同步方法会报错，async 方法通过，调用处类型正确）：
        Cache(...)    : <This, R>(target: (this: This) => Promise<R>,
                                  ctx: ClassMethodDecoratorContext<This, (this: This) => Promise<R>>) => (this: This) => Promise<R>
        SubCache(...) : <This, T, R>(target: (this: This, value?: T) => R | Promise<R>,
                                  ctx: ClassMethodDecoratorContext<This, (this: This, value?: T) => Promise<R>>)
                                  => (this: This, value?: T) => Promise<R>
        @SubCache 方法“参数可选 + 声明为 async”是 TS 装饰器改不了方法签名导致的硬约束，需要写进 README 和 JSDoc。

三、中

[中-1] getter 同步抛错时 pending 永远不会被清除，之后 reload() 全部卡死
  位置：src/cacher.ts:65-75、src/cacher.ts:85
  现象（运行时验证）：getter 同步 throw（`() => { throw … }`，或 @Cache 装饰的非 async 方法，见高-2）时，
        runGetter 是 async 函数，`finally { this.pending = empty }` 在同步抛错时会【先于】
        85 行 `this.pending = this.runGetter()` 的赋值执行，于是 pending 被赋成一个已 reject 的 promise 后再也不清；
        之后 `loading` 恒为 truthy，reload()/get() 永远直接返回这个旧的 rejected promise，再也不会重试。
        直接用 Cacher 和用 @Cache + initializeDecoratedCaches 都复现：第二次仍拿到旧错误，getter 调用次数为 1。
  修复：runGetter 开头加一个 `await undefined`（保证 finally 在赋值之后执行），
        或在 reload() 里用 `.finally` 清 pending，或用 `Promise.resolve().then(() => getter…)` 包一层。

[中-2] 装饰器参数校验：仍有遗漏与冗余
  位置：src/decorator.ts:36-47、src/decorator.ts:87；src/cacher.ts:44 构造函数
  - `ttl = Infinity` 已有默认值，45 行 `ttl !== undefined` 恒真，冗余。
  - 仍不校验 NaN / 负数（验证：均不报错）：NaN 使 `elapsed >= NaN` 恒 false，等同 Infinity（静默）；Cacher 构造函数同样不校验。
  - id 不合法时的报错仍是 “expects an options object with at least an 'id' property”，
    不如 “'id' must be a string or symbol” 准确。
  - `SubCache(formId: string)` 仍只收 string，而 `Cache` 的 id 是 `string | symbol`，symbol id 无法被 @SubCache 引用。

[中-3] @SubCache 的前置错误是同步抛出，而其余错误是 reject
  位置：src/decorator.ts:106-110
  现象（运行时验证）：@Cache 未初始化时调用，@SubCache 方法是同步 throw，@Cache 方法则返回被 reject 的 Promise。
        `obj.sub().catch(...)` 抓不到这个错误，两者对“未初始化”的表现不一致。
  建议：SubCache 包装函数改为 async，或把检查放进 Promise 里统一 reject。

[中-4]【新】后台刷新（getSync 触发）失败时必然产生 Unhandled Rejection，README 给的处理办法无效
  位置：src/cacher.ts:121-123
  现象（运行时验证）：过期后调用 getSync()，再按 README 所说给 `cacher.loading` 挂上 `.catch`，
        仍然得到一条 unhandledRejection（'refresh boom'）。Node 默认遇到 unhandled rejection 会让进程退出。
  原因：loading 是 runGetter 的 promise；getSync 里 `this.reload()` 返回的是另一个 promise（async 函数包了一层），
        它被丢弃，reject 时无人处理。用户拿不到这个 promise，无论怎么写都没法处理。
  说明：排除项里约定了“后台刷新失败由用户处理”，但现在用户只剩一种办法：让 getter 永不 reject。
        README “attach a handler if nothing awaits reload()/loading” 这条做不到。
  修复：getSync 里写 `this.reload().catch(() => {})`（错误仍可从 loading 观察到），并在 README 写明。

[中-5]【新】首次加载进行中时调用 get() 直接 reject “Cache is empty”，不会等待正在进行的加载
  位置：src/cacher.ts:101-104；@SubCache 的同类检查在 src/decorator.ts:108
  现象（运行时验证）：`c.reload(); await c.get()` → rejects "Cache is empty and has not been initialized yet."。
        对 @Cache 来说，就是 initializeDecoratedCaches() 还没 resolve 时（例如服务启动阶段就进来的请求）
        `await obj.cfg()` 会失败，哪怕加载马上就完成。
  说明：get() 已经是 async，等待成本为零：`if (!this.inited) { if (this.pending !== empty) return this.pending; throw … }`。
        getSync 无法等待，继续抛错即可。如果有意如此，请在 README 写明“初始化必须 await 完成”。

[中-6]【新】子类覆写 @Cache 方法的行为未定义
  现象（运行时验证）：
    - 子类用【相同 id】覆写：`new` 时抛 `Duplicate cache id "load" for the same instance.`；
      这是覆写方法时最自然的写法（还能让父类的 @SubCache('load') 继续指向它），现在会直接报错。
    - 子类用【不同 id】覆写：父、子两个 cacher 都会注册，initializeDecoratedCaches 会把两个 getter 都执行一遍
      （父类那个只能通过 super.load() 访问，往往是一次白发的请求）。
  建议：明确设计（例如同 id 时子类替换父类），并写进 README。

  - `@Cache()` / `@Cache(ttl)` / `@Cache(key, ttl)` → 代码是 `@Cache({ id, ttl? })`，id 必填。
  - `new Cacher<ConfigSubs, typeof loadRemoteConfig>(...)`：第二个泛型现在是“值类型”。
  - “Sync and async getters”一节：按决定改成“getter 一定返回 Promise，推荐使用 async”，reload() 恒返回 Promise。
  - `getSub()` 现在是 async：会 `await this.get()`，README 仍写“同步、不触发 reload”（另见高-1）。
  - @SubCache：现在返回 Promise，父未初始化时同步抛错；README 写的“同步 getter 时直接返回值”已不成立；

  - 只在 esbuild/tsdown 下能用（见严重-1 a），修好之前至少要写明。

[文档-2] 注释与行为不符 / 遗留代码
  - cacher.ts:50 `initialized` 注释 “Checks if the cache is empty” 语义相反（应为“是否已成功加载过”）。
  - cacher.ts:58 `setThis` 注释 “If the cache is empty, it will trigger a reload.” 实际不会触发 reload。
  - cacher.ts:99 `get()` 注释 “it will trigger the initialization”：实际是触发 reload 并等待其结果。
  - cacher.ts:189-193 遗留的被注释掉的试验代码。
  - decorator.ts:93-95、98 SubCache 内 “Although to @Cache, here is settled” 等注释不通顺。
  - mapper 能否 async 前后矛盾：derive JSDoc（cacher.ts:132）写 “pure sync … called without `await`”，
    SubCache JSDoc（decorator.ts:83）写 “must be SYNC”，但 getSub（cacher.ts:180）实际 `await` 了 mapper，
    而且 @SubCache 只有写成 async 才能通过类型检查（见高-2）。需要统一。
  - cacher.ts getOrDerive 的参数名 `pureMapFn` 与 JSDoc 的 `@param pureMapper` 不一致。
  - decorator.ts `formId` 应为 `fromId`（或直接叫 `id`）。

[导出-1] initializeDecoratedCaches 仍未从 src/index.ts 导出

[低-1] implements/old1.ts 是旧版实现（含 clear()/clearAfterPromise），仍被 tsconfig include 编译，

[低-4] getOrDerive 在 name 已存在但 mapper 不同时静默忽略新 mapper（只在首次登记时生效），README 未说明。
[低-5] getSub 以 Object.is 判等：getter 每次返回新对象（常见的 fetch().json()）时，每次刷新后派生值都会重算，

[低-6]【新】泛型顺序 `Cacher<Subs, T>`：TS 不支持部分推断，只要显式写了 Subs，T 就退化为 any。
      类型验证：`new Cacher<{ doubled: number }>(async () => 'str', 1000)` 之后 `get()` 是 any，
      `derive('doubled', x => x.not.a.real.property)` 也能编译。可考虑把 T 放到第一位，或让 derive 自己推断子类型。
[低-7]【新】Cache 初始化器里 `cachers.add(cacher)`（decorator.ts:67）在重复 id 检查之前：
      重复 id 导致 new 失败后，这个半成品实例的 cacher 仍留在全局集合里，
      initializeDecoratedCaches 会照样执行它们的 getter（验证：失败实例上的 getter 被调用了 2 次）。把检查移到 add 之前即可。
