实测：`npx vitest run packages/cacher-ts` → 30 failed / 52 passed；

严重
------------------------------------------------------------------

[严重-1] ttl 默认值失效 —— `new Cacher(getter)` 与 `new Cacher(getter, Infinity)` 必然抛错，
         "不传 ttl" 这条主路径整个不可用，并连带击穿全部 `@Cache`。
  机理（src/cacher.ts:66-71、25-39）：
      constructor(…, ttl: number | bigint = Infinity, …) { this.ttl = validTTL(ttl); }
  默认值是 number 的 `Infinity`，而 validTTL 的 number 分支要求
  `Number.isSafeInteger(ttl)` —— Infinity 不是安全整数，直接落到 throw。
  旧实现里那句 `if (ttl !== Infinity)` 的特判在本次提交中被删除。
  实测：
      new Cacher(async () => 1)             → TypeError: ttl must be a non-negative number or bigint.
      new Cacher(async () => 1, Infinity)   → 同上
      new Cacher(async () => 1, 0)          → ok
      new Cacher(async () => 1, 60000n)     → ok
  validTTL 自己的 JSDoc 写着「Cannot be `NaN`, can be `Infinity`」，与代码完全相反。
  @Cache 全量陪葬（src/decorator.ts:94-96）：
      let { id = context.name, ttl } = Object(options);
      … new DecCacher(target, ttl, this, id) …
  不传 ttl 时 `ttl === undefined`，Cacher 的构造签名把 undefined 与缺省同等看待，
  于是仍取默认的 `Infinity` → 仍抛错。因此 `@Cache()`、`@Cache({ id: 'x' })`
  都会在**首次调用被装饰方法**时抛，而非构造实例时。
  实测：装饰器用例 19/19 全红，栈顶都是 `decorator.ts:7 → cacher.ts:71`。
  修法：validTTL 放行 `Infinity`（number 分支加 `ttl === Infinity` 特判，映射为哨兵 bigint
  或另留一个 neverExpires 标志），或在解构处给 `ttl` 补显式默认值，两者最好都做。
-- 已修改

[严重-2] destroy() 后 `initialized` 变成 `null`，公开 API 违反自己的类型契约。
  本次提交把 `inited = false` 改成 `inited = null as any`，好让新的
  `get destroyed() { return this.inited === null }` 能工作。代价是：
      cacher.initialized   // 类型声明 boolean，实际返回 null
  实测（destroy 前后）：`true` (boolean) → `null` (object)。
  测试 `destroy() > clears the cached value and the initialization flag` 因此转红。
  注：destroy 后调用 `get()` 会 resolve 出 `null` 这一点**不是本次引入的**
  （老代码 destroy 把 `pending` 置 null，`pending !== empty` 为真，get() 同样 resolve null，
  已用旧逻辑单独跑过复现）。本次只是把破坏面从 get() 扩大到了 initialized 的契约。
  destroyed 的实现方式也偏脆：用「inited 是否为 null」同时编码「是否初始化」和「是否销毁」
  两种语义，而这个字段是 `/* @internal */` + stripInternal 的私有成员。
  建议独立一个 `private destroyedFlag = false`，`inited` 恢复 boolean。

-- 已保持inited的值，改为对getter判定。这是我专门设计的效率方案，无需在意，只要对外正确即可

[高-1] 时间精度被 floor 到整毫秒，且在两处各截断一次。

  改动前 `last` 存 `performance.now()` 的浮点值（实测 104.885…），
  `get()` 里做浮点差比较；改动后 runGetter 与 get() 各写一次
  `BigInt(Math.floor(performance.now()))`，精度从亚毫秒砍到整毫秒。
  对秒级 TTL 无实际影响，但 floor + BigInt 的写法重复两处：
  抽成一个私有 `private now(): bigint` 更好，也避免两处将来不一致。
  实测 `performance.now()` 在 node 24.5 为亚毫秒浮点，无小数部分时 floor 无副作用。
--已修复


[高-2] number 分支的校验上限被悄悄放开，但错误信息、JSDoc、README、测试四方没跟上。

  旧代码拒绝 `> 2147483647`；新代码只拒绝 `!Number.isSafeInteger`，
  于是 `2147483648` 现在被接受（测试 `rejects a above 2^31-1 ttl` 因此转红）。
  若这是「随 bigint 一起放开」的有意为之，那么：
      - decorator.ts:86 的 @param 仍写「must be a non-negative number between 0 and 2**31 - 1」；
      - README 的 Cacher 参数表与 @Cache 选项表 ttl 行仍写 `number` + 「safe integer」；
      - tests 仍断言 2^31-1 被拒。
  代码 / JSDoc / README / tests 四方不一致，应以「非负且由 Number.isSafeInteger 界定」
  为准统一改写（或恢复旧上限，二选一，别停在中间态）。
--请你帮我改

[高-3] bigint 分支不校验负值 —— `new Cacher(fn, -1n)` 直接通过（实测 ttl = -1n）。

  number 分支明确拒绝负数，bigint 分支却原样返回；JSDoc 声称
  「Must be a non-negative number or bigint」。负 bigint 会让每次 get() 都判定过期（恒真），
  等于把 ttl 静默降级成 0，属于「配错不报错」。补 `if (ttl < 0n) throw new TypeError(…)`。
--已修复

五、低
------------------------------------------------------------------

[低-1] implements/old1.ts 是旧版实现（含 clear()/clearAfterPromise 方案），仍被 tsconfig include
      编译，与现行 API 冲突且无说明；建议移出 src 范围或在文件头标注为历史草稿。
[低-2] package.json：`scripts.test` 使用 `clear && vitest`（非交互/CI 环境下 clear 可能报错，
      且 vitest 默认进入 watch 模式）；缺少 `sideEffects: false`；
      无 `engines` 字段（使用了 performance.now、WeakKey 类型）。
      另：package.json 末行缺换行符（0.6.0 起）。
[低-3] Cacher 的 private 成员用 `/* @internal */` + stripInternal 从 .d.ts 中剥除，
      发布后的 Cacher 类型变为无私有成员的结构类型，丧失名义性。
      （runGetter 漏标 `/* @internal */` 的问题已修复，见文件头。）
[低-4] getOrDerive 在 name 已存在但 mapper 不同时，静默忽略新 mapper（只在首次登记时生效）。
      README 现已说明此行为，但 JSDoc 尚未更新。
[低-5] getSub 以 Object.is 判断父值是否变化：getter 每次返回新对象（常见的 fetch().json()）时，
      每次刷新后派生值都会重算，没有可选的深比较 / 自定义 equals 参数。
[低-6] 泛型顺序 `Cacher<Subs, T>`：TS 不支持部分推断，只要显式写了 Subs，T 就退化为 any。
      类型验证：`new Cacher<{ doubled: number }>(async () => 'str', 1000)` 之后 get() 为 any，
      `derive('doubled', x => x.not_exist)` 也能编译通过。
      建议：将 T 放到第一位，或让 derive / getSub 各自推断子类型，与 Subs 解耦。
[低-7] @Cache 的 `id` 类型声明为 `string`，但实现按 `string | symbol` 使用
      （`cacherMap` 的第二层键、`context.name` 可能是 symbol）。
      用 symbol 命名的方法配 `@Cache()` 可以正常跑通（实测），但 `@Cache({ id: Symbol() })`
      会被类型挡下。若确实要支持 symbol id，应放宽声明；否则建议在实现里把
      `context.name` 显式 `String(...)`，避免声明与实现两张皮。
