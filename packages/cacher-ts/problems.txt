cacher-ts 问题清单
==================
范围：src/cacher.ts、src/decorator.ts、README.md、tests/、package.json
说明：已排除“文档/注释中已约定、代码选择信任”的事项（例如：getter 自行处理错误、后台刷新失败由用户处理、
      mapper 必须是纯同步函数、@Cache 方法不得带参数、@SubCache 须先让 @Cache 初始化、
      cachers 集合不注销（Nestjs 风格，实例常驻）、子类 @SubCache 以实例为键 等）。
      下列“运行时验证”均为实际运行（esbuild 按 TC39 装饰器转译 + node 24）得到的结果。
等级：[严重] 功能不可用/数据错误；[高] 明显行为缺陷；[中] 不稳定/不完善；[低] 细节/文档。
已解决并删除：cachers 泄漏（设计如此）、initializeDecoratedCaches 语义、装饰后方法返回类型、
      脱离接收者调用、SubCache 继承、reload/pending 时序（runGetter）、Cache 选项里 symbol 的校验。

------------------------------------------------------------------
一、严重
------------------------------------------------------------------

[严重-1] 重写后的 metadata 逻辑无效：@SubCache 永远找不到 map、重复 id 检测不生效（此前标记“完成”，实际未修好）
  位置：src/decorator.ts:60-65（Cache）、src/decorator.ts:102（SubCache）
  现象（运行时验证）：
    a) `(ctx.metadata as Metadata) = { [sym]: ... }` 是把【当前这个 context】的 metadata 属性换成新对象，
       并没有修改共享的 metadata 对象。每个被装饰的方法拿到的是不同的 context，因此
       - 同类里的 @SubCache 读到的 context.metadata 依旧没有 [sym]；
       - 每个 @Cache 都各建一个自己的 WeakMap，互相看不到。
    b) 因此“重复 id 会报错”并未生效：同一个类里两个 @Cache({id:'k'}) 不报错，各自照常工作
       （本地补丁后才会得到 `Duplicate cache id "k" for the same instance.`）。
    c) @SubCache 里 `?.[sym].instanceToCacheMap`（102 行）漏了第二个 `?.`：
       `@Cache` + `@SubCache` 的类在 new 时直接抛
       "Cannot read properties of undefined (reading 'instanceToCacheMap')"；
       没有任何 @Cache 的类里，本该抛的 `'cacheMap' ... not found.` 也走不到。
       （这就是最初“严重-1”的同一处，Cache 一侧改了，SubCache 一侧没改。）
  复现：`class A { @Cache({id:'a'}) async a(){…}  @SubCache('a') b(x){…} }; new A()` → TypeError。
  修复：往共享 metadata 上写，而不是替换：
        `const meta = ctx.metadata; (meta[sym] ??= { instanceToCacheMap: new WeakMap() })`；
        SubCache 一侧 `meta?.[sym]?.instanceToCacheMap`。
        重复 id 若要在装饰阶段（类定义时）报错，还需要在 metadata 上记录 id 集合；
        现在的做法是在每个实例的 initializer 里检查，必须 new 才报错。
        （验证：用上述两处最小补丁后，basic + SubCache 正常、dup id 能报错、无 @Cache 时给出友好错误。）
  附：metadata 在没有 Symbol.metadata 的环境下为 undefined，`meta[sym] = …` 会直接抛错，建议明确行为。
  附：测试没有覆盖装饰器（见测试-2），所以这两处没被发现。

二、高
------------------------------------------------------------------

[高-1] getSub 在“未加载就 derive”时返回 Symbol（empty 泄漏）
  位置：src/cacher.ts:175
  现象（运行时验证）：
    const c = new Cacher(async () => 3, 1000); c.derive('x', v => v + 1);
    await c.getSub('x')   // → Symbol()，而不是抛“未初始化”
  原因：derive 时 sub.parent 初始值是 empty，未加载时 this.cache 也是 empty，
        `Object.is(sub.parent, this.cache)` 为 true，直接把 sub.cache（empty）当结果返回。
        getOrDerive 也走同一路径。
  修复：判断里加上 `this.inited`（或 `this.cache !== empty`）；或把快速路径放到 `await this.get()` 之后。

[高-2] @SubCache / getSub 仍不会触发父缓存的 TTL 刷新（此前“已改为 parent = this.get()”只覆盖了慢路径）
  位置：src/cacher.ts:174-182
  现象（运行时验证）：@Cache({ttl:50}) + @SubCache，已读过一次派生值后等待 80ms 再读：
        派生值不变、getter 调用次数不变（仍为 1）。
  原因：getSub 先做 `Object.is(sub.parent, this.cache)` 快速返回，只有 parent 变化后才 `await this.get()`；
        所以“父值没变”的常态下永远不会检查 ttl，只读派生视图的用法等于永不过期。
        （只有父值被别处刷新、或首次计算时才会调到 get()。）
  修复：把 `const parent = await this.get()` 放到判等之前（过期时 get 内部 reload，等待后拿到新值），
        再用 `Object.is(sub.parent, parent)` 判断；注意要和 getSync 风格的“后台刷新”区分开，
        目前 getSub 是 async，语义上应等待新值。
  如果就是想“派生视图不续期”，请在 README 明确写出来。

三、中
------------------------------------------------------------------

[中-1] getter 同步抛错时 pending 永远不会被清除，之后 reload() 全部卡死
  位置：src/cacher.ts:66-86
  现象（运行时验证）：getter 是普通函数且同步 throw（类型上要求返回 Promise，但 `() => { throw … }`、
        `() => JSON.parse(x) && fetch()` 这类写法很常见）。
        runGetter 是 async 函数，`finally { this.pending = empty }` 在同步抛错时会【先于】
        `this.pending = this.runGetter()` 的赋值执行，于是 pending 被赋成一个已 reject 的 promise 后再也不清；
        之后 `loading` 恒为 truthy，reload()/get() 永远直接返回这个旧的 rejected promise，再也不会重试。
  修复：runGetter 开头加一个 `await undefined`（让 finally 一定在赋值之后执行），
        或在 reload() 里用 `.finally` 清 pending，或用 `Promise.resolve().then(() => getter…)` 包一层。

[中-2] 装饰器参数校验：仍有遗漏与冗余
  位置：src/decorator.ts:35-47、src/decorator.ts:89；src/cacher.ts 构造函数
  - `ttl = Infinity` 已有默认值，`ttl !== undefined` 恒真，冗余。
  - 仍不校验 NaN / 负数：NaN 使 `elapsed >= NaN` 恒 false，等同 Infinity（静默）；Cacher 构造函数同样不校验。
  - id 不合法时的报错信息仍是 “expects an options object with at least an 'id' property”，
    不如 “'id' must be a string or symbol”准确。
  - `SubCache(formId: string)` 类型仍只收 string，而 `Cache` 的 id 是 `string | symbol`，symbol id 无法被 @SubCache 引用。

[中-3] @SubCache 的前置错误是同步抛出，而其余错误是 reject
  位置：src/decorator.ts:104-109
  现象：被装饰方法返回的是 Promise（getOrDerive → getSub 是 async），但 “Cacher not found or initialized”
        是同步 throw。`obj.sub().catch(...)` 抓不到这个错误，而 `@Cache` 方法在未初始化时是 reject（Cacher.get 是 async）。
        两者对“未初始化”的表现不一致。
  建议：SubCache 包装函数改为 async，或把检查放进 Promise 里统一 reject。

四、文档、注释与测试（不完善） —— 整体上改完后重写。
------------------------------------------------------------------

[文档-1] README 尚未随这次重写更新（与实现严重脱节，会直接导致用户写出无法工作的代码）
  - 主打“同步读取 get(): T”，现在是 `get(): Promise<T>`，同步读是 `getSync()`（README 未提及 getSync）。
  - `isInitialized` → 代码是 `initialized`。
  - `@Cache()` / `@Cache(ttl)` / `@Cache(key, ttl)` → 代码是 `@Cache({ id, ttl? })`，id 必填。
  - `new Cacher<ConfigSubs, typeof loadRemoteConfig>(...)`：第二个泛型现在是“值类型”。
  - “Sync and async getters”一节：按决定改成“getter 一定返回 Promise，推荐使用 async”，reload() 恒返回 Promise。
  - `getSub()` 现在是 async：会 `await this.get()`（会等待过期刷新），README 仍写“同步、不触发 reload”。
  - @SubCache：现在返回 Promise，父未初始化时同步抛错；README 写的“同步 getter 时直接返回值”已不成立；
    “通过写在实例上的 registry 访问”实际是 metadata 上的 WeakMap。
  - README 没提 initializeDecoratedCaches（也没有导出，见导出-1）。
  - “Zero dependencies”：源码引用 `@shared/std/map.js`，需确认构建产物把它内联。

[文档-2] 注释与行为不符 / 遗留代码
  - cacher.ts:50 `initialized` 注释 “Checks if the cache is empty” 语义相反（应为“是否已成功加载过”）。
  - cacher.ts:58 `setThis` 注释 “If the cache is empty, it will trigger a reload.” 实际不会触发 reload。
  - cacher.ts:189-193 遗留的被注释掉的试验代码。
  - decorator.ts SubCache 内 “Although to @Cache, here is settled” 等注释不通顺。
  - decorator.ts SubCache 的 JSDoc 写 “Decorated method must be SYNC”，与 getSub 现在 `await` mapper 的行为并存，
    请明确：mapper 是否允许 async（目前 `await sub.fn.call` 实际支持，但类型写成同步）。
  - cacher.ts getOrDerive 的参数名 `pureMapFn` 与 JSDoc 的 `@param pureMapper` 不一致。

[导出-1] initializeDecoratedCaches 仍未从 src/index.ts 导出
  现象：公开 API（有 JSDoc），但包入口只导出 Cacher/Cache/SubCache，用户无法使用；
        而 @Cache 之后必须先调用它，否则 get() 抛 “Cache is empty”。
  另外 Metadata / SubCacheEntry 等类型未导出。

[测试-1] 测试仍基于旧 API，30/37 失败，且有 14 个 Unhandled Rejection（npx vitest run packages/cacher-ts）
  原因：同步 getter、`load()`、`isInitialized`、get 同步返回、getSub 同步等旧语义。
  需要按新 API 重写（get / getSync / reload / loading / getSub 为 async）。

[测试-2] 装饰器零覆盖
  建议补充：基本缓存、每实例隔离、同类/继承下重复 id 检测、@Cache + @SubCache 联用、
  @SubCache 的 TTL（高-2）、未 derive 先读（高-1）、getter 同步抛错后重试（中-1）、
  无 @Cache 的 @SubCache、initializeDecoratedCaches（含 force）。
  另外 vitest 当前配置（oxc）无法直接解析 TC39 装饰器语法，需要在 vitest/tsconfig 里启用装饰器转译。
