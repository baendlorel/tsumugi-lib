# JSONPC 边缘情况问题清单

## 当前规则回顾

1. Only `//` comments.
2. Comments should occupy the whole line.
3. Only appears above property names
4. One property name can have multiple comments.
5. Properties in arrays cannot be commented.

## 需要明确的边缘情况

### 1. 根级别的注释
```jsonc
// 这是用户配置
{
  "name": "test"
}
```
**问题**：根 `{` 之前的注释属于谁？
- A. 作为文件级注释保留
- B. 绑定到第一个属性
- C. 当作语法错误

我已经明确说了，注释只允许出现在字段上方，你说的这个位置，是要报错的。
但是我觉得，可以允许注释存在于整个文件的开头，因为这里的解析没有压力，不需要任何绑定，回写的时候也很简单。

### 2. 嵌套对象的开头注释
```jsonc
{
  "user": {
    // 用户详细信息
    "name": "test"
  }
}
```
**问题**：内层 `{` 之后、属性名之前的注释如何处理？
- A. 绑定到下一个属性（`name`）
- B. 当作对象级注释
- C. 当作语法错误

这是合法的，同样属于属性名的注释，具体的解析方法我会亲自编写，你先不用担心。

### 3. 数组值本身的注释
```jsonc
{
  // 用户标签列表
  "tags": ["a", "b", "c"]
}
```
**问题**：数组值能否被注释？
- A. 可以，绑定到 `tags` 属性
- B. 不可以，当作语法错误

这是合法的，也是属于属性名的注释

### 4. 根为数组的情况
```jsonc
// 用户列表
[
  {"name": "a"},
  {"name": "b"}
]
```
**问题**：根是数组时如何处理？
- A. 数组前的注释作为文件级注释
- B. 不支持根为数组
- C. 其他处理方式

数组的方式我最后说

### 5. 结尾注释
```jsonc
{
  "name": "test"
}
// 配置结束
```
**问题**：`}` 之后的注释如何处理？
- A. 允许，作为文件级注释
- B. 当作语法错误
- C. 忽略
结尾注释和开头注释一样，也允许存在，也允许多行//的注释，这个解析起来也简单，没有压力

### 6. 空对象/空数组
```jsonc
{
  // 空对象占位
  "empty": {}
}
```
**问题**：空对象/数组前的注释如何处理？
- A. 绑定到属性
- B. 不允许这种情况
- C. 其他处理方式
这也是属性名注释

### 7. 多行字符串的处理
```jsonc
{
  // 描述信息
  "description": "这是第一行
这是第二行"
}
```
**问题**：虽然标准 JSON 不支持多行字符串，但如何处理格式化后的情况？
- A. 按标准 JSON 处理（不支持）
- B. 尝试支持扩展格式
- C. 其他
这也是属性名注释

### 8. 数组内对象的属性注释
```jsonc
{
  "users": [
    {
      // 第一个用户
      "name": "a"
    },
    {
      // 第二个用户  
      "name": "b"
    }
  ]
}
```
**问题**：数组内对象的属性能否注释？
- A. 可以（规则5说"数组中的属性"，可能指数组值本身而非数组内对象的属性）
- B. 不可以
- C. 需要澄清规则5的含义
数组我最后说

# 数组相关
原本我觉得数组里东西不唯一，难以注释，但是现在我有这样的想法：
1、注释在数组元素上
```json
"arr":[
  // 第一项注释
  1,
  2,
  3,
]
```
这种情况，算是这个数组的属性名arr[0]上的注释
2、数组项内部的注释
```json
"arr":[
  {
    // 名字
    "name":"sdf"}
]
```
那就算做是arr[0].name的注释。
3、顶层是数组
如果顶层是数组，那么1和2中的arr将记录为`null`，用于区分，因为顶层的数组确实没有属性名字。
